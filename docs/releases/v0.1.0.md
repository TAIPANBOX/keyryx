# keyryx v0.1.0

The first release of keyryx: key custody and an independent witness for the agent-governance record of the TAIPANBOX stack. One binary, two roles, never in one process. Neither role sits on a request path.

Tag: `v0.1.0`. Image: `ghcr.io/taipanbox/keyryx:v0.1.0`, `linux/amd64` and `linux/arm64`. There is no moving tag (no `latest`, no `main`). The image is signed keyless with cosign by digest and carries a build-provenance attestation. The release page carries SPDX and CycloneDX SBOMs of the source tree this build was made from, and a provenance attestation for them.

## What it is

- **Custody** (`keyryx custody`) holds signing keys, signs low-rate statements for the consumers its policy grants a key to, certifies the short-lived keys that high-rate signers hold themselves, and publishes each key set with an overlap, so a rotation is never an outage.
- **The witness** (`keyryx witness`) reads the record read-only, checks that every byte it saw before is still there, attests to each new trailryx store root, and keeps its own append-only log. Its tree heads are signed with ECDSA P-384 and ML-DSA-65 side by side.
- **Offline checks** (`keyryx verify`) check a witness log, or streams and their checkpoints, from files alone. An empty directory is reported as measured nothing, never as OK.

It is not an identity provider for agents, not a holder of provider keys, not a decision point, and not a metered service. Nothing in it calls a paid API.

## What custody does

- **Keys** of three algorithms: ES256, ES384 and ML-DSA-65 (FIPS 204, Go 1.27's `crypto/mldsa`). Each key is one file under `KEYRYX_DATA/keys/<name>/`, with its private half wrapped under AES-256-GCM. The wrapping key is derived from the root key and bound to the key's name, id and algorithm. A record that is moved, edited or swapped refuses the start.
- **A root key** in a file only its owner can read: 64 hex characters, group and other permission refused.
- **A state MAC** on every key and statement record. A record whose MAC does not hold is treated as revoked: it is never published or used, and it raises an alarm on stderr, on the use log and in `GET /v1/state` until an admin revokes the key it names.
- **A delegation root**: two keys of one generation, ES384 and ML-DSA-65, in the reserved `keyryx.` name space. It signs key statements and nothing a request chose.
- **Delegated keys**: a high-rate signer proves possession of its own key and receives a key statement, a JWS with exactly the ES384 and ML-DSA-65 halves of the root. A key id is certified once, a revoked one is never published or certified again, and at most four keys per name are live at once.
- **A use log** (`KEYRYX_DATA/use.ndjson`): one line per signature, statement, rotation and revocation, each naming the SHA-256 of the line before it. A signature or statement is answered only after its line is on disk. The log holds the digest of what was signed, never the statement.
- **Consumers** authenticate one way each: a unix socket of their own, a bearer key compared by digest in constant time, or a Kubernetes projected service-account token verified against the cluster's keys for this service's audience.

Routes: `GET /healthz`, `GET /v1/state`, `GET /v1/keys`, `GET /v1/jwks/{name}`, `GET /v1/statements/{kid}`, and the consumer and admin routes `POST /v1/keys/{name}/sign`, `POST /v1/keys/{name}/challenge`, `POST /v1/keys/{name}/delegate`, `POST /v1/keys/{name}/rotate` and `POST /v1/kids/{kid}/revoke`. A refusal answers its status and nothing else; the reason goes to the operator's log.

## What the witness does

Every `KEYRYX_WITNESS_INTERVAL` it reads, without writing to what it reads:

- **Every stream** (`*.ndjson`) in `KEYRYX_WITNESS_EVENTS`. It keeps the bytes it has read and their SHA-256, the `prefix` of agent-passport SPEC 6.5.1, and hashes the stream again from byte zero each interval. A changed byte is reported as a rewrite, a shorter stream as a truncation, and a new chain mid-stream as a restart.
- **Every checkpoint file** in `KEYRYX_WITNESS_CHECKPOINTS`, checked by the steps of SPEC 6.5.1 format v1. Each checkpoint is signed by a key that custody certifies for the stream's bound key name, and every checkpoint kept before must still hold.
- **Every trailryx data directory** in `KEYRYX_WITNESS_RECORDS`. It computes the store root as trailryx-verify does and attests to each new root with its ES384 half. A sealed manifest that is rewritten or gone is reported.

Every finding is an agent-event in `keyryx.ndjson` (or the path set in `KEYRYX_WITNESS_ALERTS`), with counts and clipped hashes and never record content. Every observation is an entry in the witness's own RFC 9162 Merkle log, and each interval ends with a signed tree head. The witness serves inclusion and consistency proofs and its own log, read-only.

## Configuration

Anything missing or malformed refuses the start with exit code 2, and the message names the variable.

### Custody

| variable | required | meaning |
|---|---|---|
| `KEYRYX_DATA` | yes | data directory, mode 0700 |
| `KEYRYX_ROOT_KEY_FILE` | yes | the root key file |
| `KEYRYX_POLICY` | yes | the policy file (version 1, at most 1 MiB), declaring keys, consumers, grants and each consumer's one way in |
| `KEYRYX_ADDR` | no | TCP listen address, default `127.0.0.1:4340` |
| `KEYRYX_SOCKET_DIR` | once a consumer uses `socket` | parent of each socket consumer's directory |
| `KEYRYX_K8S_ISSUERS` | once a consumer uses `k8s` | `issuer\|audience\|jwks-file`, one per line or comma-separated |
| `KEYRYX_ADMIN_KEYS` | no | comma-separated `sha256:<64 hex>` digests of admin keys; unset, rotate and revoke refuse every call |
| `KEYRYX_PUBLISH_AHEAD` | no | how long a next or renewed key is published before it signs; default `15m`, from one minute to one day |

### Witness

| variable | required | meaning |
|---|---|---|
| `KEYRYX_WITNESS_DATA` | yes | the witness's own data directory, mode 0700, never custody's |
| `KEYRYX_WITNESS_ROOT_KEY_FILE` | yes | the witness's own root key file |
| `KEYRYX_WITNESS_EVENTS` | yes | the bus directory it reads |
| `KEYRYX_WITNESS_CHECKPOINTS` | no | the checkpoint directory it reads |
| `KEYRYX_WITNESS_CUSTODY_URL` | once checkpoints are set | where custody serves key statements |
| `KEYRYX_WITNESS_STREAM_KEYS` | once checkpoints are set | `stream.ndjson\|key-name` per stream, comma or line separated: the delegated key name whose certified keys sign that stream's checkpoints |
| `KEYRYX_WITNESS_DELEGATION_ROOT_PIN` | no | the delegation root's kids, at least one ES384 and one ML-DSA-65, comma-separated. Unset, the first root set custody serves is pinned |
| `KEYRYX_WITNESS_RECORDS` | no | `tenant\|directory` per trailryx data directory |
| `KEYRYX_WITNESS_ALERTS` | no | where findings are written; default `keyryx.ndjson` in the events directory |
| `KEYRYX_WITNESS_ADDR` | no | default `127.0.0.1:4341` |
| `KEYRYX_WITNESS_INTERVAL` | no | default `1m`, from one second to one hour |
| `KEYRYX_WITNESS_FULL_BYTES` | no | a stream over this many bytes is hashed from zero only every `KEYRYX_WITNESS_FULL_INTERVAL`; default 256 MiB |
| `KEYRYX_WITNESS_FULL_INTERVAL` | no | default `1h` |
| `KEYRYX_WITNESS_SEAL_EVERY` and `KEYRYX_WITNESS_SEAL_LINES` | no | a seal's worth, for the missing-root finding; default `15m` and 4096 lines |
| `KEYRYX_WITNESS_NAME` | no | the name in its attestations; default `keyryx-witness` |
| `KEYRYX_WITNESS_TSA_URL` | no, opt-in | an https RFC 3161 time-stamping authority. Unset, no authority is called |
| `KEYRYX_WITNESS_TSA_CA` | once a TSA is set | the PEM root its tokens must chain to |
| `KEYRYX_WITNESS_TSA_EVERY` | no | default `1h`, from ten minutes to a day |

Time-stamping is off by default. An outbound call to a third party happens only when the operator names an authority.

## Breaking changes and migration

None. This is the first release, so there is no earlier version to break. Nothing is migrated.

## What the release guards against

- An edited key or statement state on disk being taken as true: every such record carries a MAC under a key derived from the root key, and a record that does not hold is treated as revoked and reported (commit `28af6bd`).
- A signature or statement answered without its line on the use log (use log with a hash chain; a break in the middle refuses the open).
- A key set that still publishes a revoked key, or a key that signs before verifiers can hold it (rotation publishes the next key first).
- A witness that reads a stream it has already seen changed, a checkpoint not signed under the bound key, or a log edited or reordered (commit `43bb8c4`).
- A witness or custody that starts with a default key or without its configuration: the role refuses to start.

## NOT PROVEN

Stated here as the README states them.

- **trailryx does not attach the attestations yet.** `trailryx-node` takes no witness input, so the attestations the witness writes are files beside its log until trailryx reads them into its packs; `trailryx-verify` would check them as it checks any witness, which this repository has not run.
- **The store root is trailryx's construction rebuilt by hand.** It is checked against trailryx's source at 92dd4b6 by a reference written separately in the tests, not against a store trailryx itself sealed: no trailryx build has run here.
- **A rewrite that also shortens a stream is reported as a truncation.** The witness knows the bytes are not the ones it saw; with fewer bytes than it read, it names the shrinking.
- **The cost of re-reading is not measured.** Each interval hashes every stream under `KEYRYX_WITNESS_FULL_BYTES` from byte zero; how long that takes on a real bus has not been measured.
- **No time-stamping authority has been asked.** The RFC 3161 client is tested against an authority the tests build, with ECDSA and RSA keys; no public authority's token has been verified by it.
- **The first root is taken on first use.** With no `KEYRYX_WITNESS_DELEGATION_ROOT_PIN`, the witness pins whatever root set custody serves at its first read; a set swapped before that read is pinned. An operator closes that window by setting the pin from the published delegation root before the witness first starts. A real rotation of the delegation root reads as a changed root until an operator pins the new set, and no rotation has been run against a witness here.
- **The witness reads the bus and the record, not custody's use log**, and custody writes no `key_rotated` or `key_revoked` event yet.
- **Nothing consumes a key statement yet.** The delegation service, the producers' checkpoint writers and the shared key client that would ask for and renew delegated keys are later pull requests in their own repositories; the round trip with the estate's shared verifier is tested here, not run by a consumer.
- **An earlier record can be put back.** The state MAC proves custody wrote a state, not that it is the latest one: whoever can write the data directory can restore a copy of a record from before its revocation, and that copy's MAC holds. The use log keeps the revocation line, and the witness is what would notice.
- **Challenges live in memory.** A restart drops the outstanding ones, and the consumer asks again.
- **A late renewal can sign before verifiers refresh.** When a name's current key ends inside the publish-ahead time, the new key is valid at once, since waiting would leave no valid key at all.
- **No real Kubernetes cluster has authenticated a consumer.** The projected token path is tested against tokens this repository mints with the claims a cluster issues; it has not run against a kubelet's token.
- **The constant-time compares are not timed.** Key and admin digests are compared with `crypto/subtle` over every configured digest; nothing measures the timing.
- **A rotation or revocation whose log line fails to write still stands.** The answer is 503 and the key's state has changed; only a signature is withheld until its line is written.
- **The use log is protected against edits in its middle, not against a rewrite from its first line.** The witness of this version does not read it.
- **No cloud key management.** The root key is a file. A KMS adapter would be metered, and it is the operator's decision, not a default.
- **Independence from a host administrator** will not come from this service alone: on one machine the witness is a separate user and volume, not a separate trust domain. An off-host anchor (a public time-stamping authority, built here and off by default, or a second witness on another machine, not built) is what closes that, and it is the operator's to switch on.
- **Post-quantum signatures** are produced with Go 1.27's `crypto/mldsa`; no verifier outside this repository checks ML-DSA yet, and the key set's AKP form follows a JOSE draft, not a published RFC.
