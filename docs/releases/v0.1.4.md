# keyryx v0.1.4

A patch release on v0.1.3. At the bound on live keys of a delegated name, a new key of an owner now retires that owner's oldest key instead of being refused, once the next key has been signing for the name's overlap. Before this release a consumer that keeps its working key in memory, as vouchryx does, spent one of the four slots on every start, and the fifth start inside 72 hours could get no key until the oldest aged out (estate gap G3.11).

## Changed since v0.1.3

- #27, `feat(certify): at the bound a new key retires its owner's oldest`. Invariant 42 in CLAUDE.md.
  - At `MaxLive` (four) a new key of an owner retires that owner's oldest key only when the owner's second oldest key has been signing for the name's overlap. A consumer signs with the newest key that has begun, so no token the old key signed can still be alive. Before that moment the new key is refused with `409 too_many_live_keys`, as before, which also holds a crash loop to three keys per publish-ahead plus overlap.
  - A retired key is not a revoked key. The witness refuses a record seen after `revoked_at`, and a restart stole nothing, so the statement stands and an admin can still revoke it.
  - A retirement is a file of its own, `KEYRYX_DATA/retired/<name>/<kid>.json`, under a state MAC of its own kind. No statement record changes form.
  - The old key leaves on disk before the new one is written, so a death between the two writes leaves one key fewer, never one more than the bound.
  - `GET /v1/keys` reads `retired` for such a key and carries its `retired` time. The use log gains a `retire` line. The retired key leaves `GET /v1/jwks/{name}` at once.
  - The same change covers tokenfuse's checkpoint key.
- #24, `deps: agent-stack-go v2.0.2` (the Go 1.27.3 rebuild).
- #7, `deps: github.com/gowebpki/jcs` 1.0.1 to 1.0.2.
- #23, `ci`: three actions bumped, among them `docker/login-action` v4.6.0 to v4.7.0 in the release workflow.
- #25, `docs(readme)`: two consumers ask keyryx for keys, and tokenfuse writes the checkpoints. A README paragraph only.
- #26, a stray `.DS_Store` removed.
- #22, the post-tag documentation of v0.1.3.

No route, variable, response code or statement form changes.

## Measured

`labs/five-starts` on forge, 2026-11-07, evidence in `labs/five-starts/evidence`. Before this change the fifth start of a consumer inside the window got no token in 240 seconds and exited 1. After it the fifth start got a token 61 seconds after it began, at the one-minute policy, and 721 seconds after it began at a box's own policy (overlap 10 minutes, publish-ahead 2 minutes) with each start waiting for its token, 1021 seconds in a burst of starts. Every run ended with four keys in the set. 16 new tests, all green with `-race`; 26 of 26 mutants caught; a sweep of 6000 schedules, then 1000 with `-race`.

## Upgrade

Pull `ghcr.io/taipanbox/keyryx:v0.1.4` and restart. No configuration, key store, policy or witness data changes. The data directory gains `retired/` at the first retirement.

Rollback: v0.1.3 opens a data directory that holds `retired/`, raises no alarm, and publishes the retired key again until its natural end, as it would have without this release.

This takes one signing process per owner of a name. Both launchers run one (`replicas: 1` with `Recreate` in stack-k8s, one compose service in stack-single).
